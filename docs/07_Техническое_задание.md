## 2. Назначение и цель

### 2.1. Назначение

Модуль предназначен для безопасного и устойчивого доступа Java-приложения к реляционной базе данных СТО: чтения справочников, создания заявок, добавления услуг, расчёта стоимости, закрытия заявок и просмотра журнала статусов.

### 2.2. Цель разработки

Создать учебный, но законченный модуль, который:

1. демонстрирует слоистую архитектуру доступа к данным;
2. использует PostgreSQL как источник бизнес-правил и ограничений;
3. обеспечивает обработку ошибок, транзакции и повторные попытки;
4. показывает корректную работу с параметрами подключения и секретами;
5. сопровождается тестами и документацией.

### 2.3. Целевая аудитория

* студент-разработчик и преподаватель;
* администратор учебного стенда;
* сотрудник СТО (менеджер, мастер) — в демонстрационном режиме;
* клиент СТО — в ограниченном режиме просмотра.

## 3. Объект и предметная область

### 3.1. Предметная область

СТО принимает автомобили, оформляет заявки, назначает мастеров, оказывает услуги и закрывает заявки. Стоимость заявки складывается из оказанных услуг с фиксацией цены на момент добавления. Изменение статуса фиксируется в журнале.

### 3.2. Основные сущности

| Сущность | Назначение |
|---|---|
| `roles`, `users` | роли и учётные записи |
| `clients` | клиенты СТО |
| `cars` | автомобили клиентов |
| `masters` | мастера |
| `services` | справочник услуг |
| `orders` | заявки |
| `order_statuses` | статусы заявок |
| `order_services` | услуги в заявке |
| `order_status_log` | журнал изменений статусов |
| `user_security` | попытки входа и блокировка учётной записи |
| `login_attempts` | журнал попыток входа |
| `v_order_total` | представление стоимости заявки |
| `v_my_orders` | представление заявок текущего клиента |

### 3.3. Бизнес-правила

1. Заявка создаётся для существующего клиента и его автомобиля.
2. Автомобиль должен принадлежать указанному клиенту.
3. Новая заявка получает статус «новая».
4. Цена услуги фиксируется в `order_services.price_at` и не меняется при изменении прайса.
5. В заявку со статусом «завершена» или «отменена» нельзя добавлять услуги.
6. При переводе в «завершена» заполняется `closed_at`; при выходе из этого статуса — очищается.
7. Любое изменение статуса записывается в `order_status_log`.
8. Стоимость заявки = сумма `price_at * quantity` по всем услугам.
9. Телефон клиента и госномер автомобиля уникальны.
10. Год автомобиля — в диапазоне 1950..2100.

### 4.3. Требования к данным

1. Схема создаётся скриптом `sto.sql`; демонстрационные данные — `docker/init/02_seed.sql`.
2. Все таблицы имеют первичные ключи; связи — внешние ключи.
3. Обязательные поля — `NOT NULL`; уникальные — `UNIQUE`; диапазоны — `CHECK`.
4. Удаление клиента каскадно удаляет его автомобили; удаление заявки — её услуги.
5. Представление `v_order_total` возвращает `order_id`, `client`, `car`, `status`, `total_cost`.
6. Представление `v_my_orders` возвращает заявки клиента, привязанного к `app.client_id`.
7. Функции и триггеры описаны в `sto.sql`; бизнес-правила не дублируются только в Java.
8. Кодировка БД — UTF-8.

### 4.6. Требования к безопасности

1. Все SQL-значения — только через параметры.
2. Пароли пользователей — bcrypt-хеши (`pgcrypto`).
3. Пароль БД — вне кода, с возможностью переопределения.
4. Роли БД — минимально необходимые права.
5. Клиент не должен получать доступ к базовым таблицам.
6. Ошибки не должны раскрывать пароли.
7. Для эксплуатации — TLS, аудит, блокировка подбора пароля.
8. Секреты не должны храниться в Git.

### 5.2. Роли

| Роль | Назначение | Права |
|---|---|---|
| `sto_admin` | администратор | полный доступ (учебный стенд) |
| `sto_manager` | мастер-приёмщик | клиенты и автомобили: `SELECT/INSERT/UPDATE`; заявки: `SELECT`, `UPDATE (status_id)`, создание через `create_order`; услуги в заявке |
| `sto_master` | мастер | чтение заявок, клиентов, автомобилей и услуг; добавление услуг; `UPDATE (status_id)` без `closed_at` |
| `sto_client` | клиент | `SELECT` на `services` и `v_my_orders`; базовые таблицы недоступны |
| `sto_readonly_group` | группа | чтение справочников |

### 5.3. Ограничения и индексы

* `UNIQUE`: `users.username`, `clients.phone`, `cars.plate_num`, `roles.name`, `order_statuses.name`.
* `CHECK`: год 1950..2100, цена ≥ 0, длительность > 0, количество > 0.
* Индексы: `orders(client_id)`, `orders(master_id)`, `orders(status_id)`, `cars(client_id)`.
* Рекомендуется добавить `order_services(order_id)`.

## 8. Порядок контроля и приёмки

### 8.1. Критерии приёмки

1. `docker compose up -d` на чистом томе завершается успешно, контейнер `healthy`.
2. `mvn package` завершается успешно.
3. `mvn test` — 59 тестов, 0 failures, 0 skipped.
4. `--check` выводит версию PostgreSQL и не печатает пароль.
5. `--demo` проходит полный цикл: создание, услуги, расчёт, закрытие, журнал.
6. 20 функциональных кейсов пройдены; негативные кейсы отклоняются.
7. SQL-инъекции не проходят.
8. Роль `sto_client` не читает базовые таблицы; клиент видит только свои заявки.
9. Роли manager и master не могут изменить `closed_at` напрямую.
10. Документация содержит все разделы и ссылки.
11. Известные ограничения зафиксированы.

### 8.2. Порядок предъявления

1. Исполнитель разворачивает стенд и запускает demo.
2. Показывает результаты тестов и evidence-файлы.
3. Отвечает на вопросы по архитектуре и безопасности.
4. Передаёт документы и артефакты по акту (задание 10).

## 10. Ограничения и допущения

1. Основной интерфейс — настольное приложение JavaFX; консольный режим `--console` сохранён как дополнительный слой поверх того же модуля доступа к БД.
2. Учебные пароли и пароль `postgres` приведены для локального стенда.
3. Приложение использует роль `sto_admin`; для эксплуатации нужна отдельная роль.
4. Нет TLS, резервного копирования и промышленного мониторинга.
5. Peer-app для обмена результатами по заданию 7 не предоставлялся.
6. Нагрузочное тестирование и SCA не выполнялись.
7. Часть сценариев устойчивости (pool exhaustion, диск, сеть) не выполнена.
8. Данные в БД демонстрационные; реальные персональные данные не используются.
