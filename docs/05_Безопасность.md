# Безопасность модуля доступа к БД СТО

**Документ:** анализ безопасности и акт передачи результатов (задания 9–10)  
**Объект:** `sto-db-module`, схема `sto.sql`, Docker-стенд PostgreSQL 16  
**Метод:** анализ исходного кода, проверка прав в `psql`, ручные атаки, изучение журналов  
**Связанные документы:** [Результаты тестирования](04_Результаты_тестирования.md), [Отчёт о тестировании](06_Отчет_о_тестировании.md)

## 1. Цель и границы анализа

Цель — оценить, может ли модуль:

1. пропустить SQL-инъекцию;
2. раскрыть пароли и секреты;
3. позволить пользователю выполнить действие вне его роли;
4. обойти бизнес-правила через прямой SQL;
5. оставить незаметным несанкционированный доступ.

Анализ охватывает учебный стенд и исходный код. Промышленная инфраструктура (WAF, SIEM, HSM, корпоративный каталог) не моделировалась. Результаты следует рассматривать как baseline для учебного проекта, а не как заключение аттестации.

## 2. Модель угроз

### 2.1. Активы

| Актив | Почему важен |
|---|---|
| Персональные данные клиентов (ФИО, телефон, e-mail) | конфиденциальность, 152-ФЗ |
| Данные автомобилей (VIN, госномер) | идентификация владельца |
| Заявки и стоимость работ | коммерческая информация, целостность расчётов |
| Учётные записи и пароли | доступ к системе |
| Журнал статусов | доказательство изменений |

### 2.2. Нарушители

| Нарушитель | Возможности |
|---|---|
| Внешний пользователь БД | знает хост/порт, может подбирать пароль |
| Клиент СТО | легитимный вход, ограниченная роль |
| Сотрудник (manager/master) | легитимный вход, широкие права на заявки |
| Недобросовестный администратор | полный доступ к БД и журналам |
| Сетевой посредник | перехват трафика при отсутствии TLS |

### 2.3. Допущения

* приложение и БД находятся в локальной сети учебного стенда;
* злоумышленник не имеет доступа к файловой системе сервера;
* резервное копирование и физическая безопасность вне рамок.

## 3. SQL-инъекции

### 3.1. Как устроена защита

Все значения передаются через параметры JDBC:

```java
String sql = """
        SELECT u.id, u.username, u.full_name, r.name AS role
        FROM users u
        JOIN roles r ON r.id = u.role_id
        WHERE u.username = ?
          AND u.password_hash = crypt(?, u.password_hash)
        """;
try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setString(1, username);
    statement.setString(2, finalPassword);
    ...
}
```

Пользовательские данные не попадают в текст SQL. Для вызовов функций используется `CallableStatement` с `?`. Динамическое построение SQL есть только в `OrderRepository.findStatusLog`, где добавляется **статическая** строка `WHERE order_id = ?` в зависимости от `orderId != null`; значение по-прежнему передаётся параметром.

### 3.2. Проверенные payload-ы

| № | Логин | Пароль | Результат | Доказательство |
|---|---|---|---|---|
| 1 | `' OR '1'='1` | `anything` | `AuthenticationException` | `manual_negative_service.txt` |
| 2 | `admin' --` | `anything` | `AuthenticationException` | автотест |
| 3 | `admin` | `' OR '1'='1` | `AuthenticationException` | `manual_negative_service.txt` |
| 4 | `"; DROP TABLE users; --` | `x` | `AuthenticationException`; таблица `users` сохранилась (4 записи) | `manual_negative_service.txt` |
| 5 | `admin` | пустая строка | `ValidationException` | `manual_negative_service.txt` |

**Вывод:** SQL-инъекции при входе не выявлены. Параметризация корректна, ошибки не приводят к выполнению пользовательского SQL.

### 3.3. Остаточные риски

* если в будущем появится динамическая сортировка/фильтр по имени колонки, потребуется белый список;
* прямой доступ к БД в обход приложения остаётся возможен для ролей с `LOGIN`;
* SQL-ошибки выводятся в консоль с деталями (до 300 символов) — для промышленного UI это лишняя информация.

## 4. Аутентификация и хранение паролей

| Аспект | Реализация | Оценка |
|---|---|---|
| Хранение паролей пользователей | bcrypt-хеш в `users.password_hash`, создаётся `crypt(..., gen_salt('bf', 10))` (в том числе функцией `app_hash_password`) | хорошо |
| Проверка пароля | в SQL `password_hash = crypt(?, password_hash)` и в функции `app_check_password`; хеш не загружается в Java | хорошо |
| Создание учётных записей | функция `create_account(...)` хеширует пароль внутри БД; `EXECUTE` выдан только `sto_admin`, у `PUBLIC` отозван | хорошо |
| Передача пароля | `char[]`, очистка `Arrays.fill(password, '\0')` в `finally` | хорошо |
| Логирование | `DbSettings.toSafeString()` не содержит пароль; в журнал не пишутся ни пароль БД, ни пароль пользователя | хорошо |
| Политика паролей | демо-пароли простые (`admin123`), требований к длине/сложности нет | риск |
| Блокировка при подборе | 3 попытки за сеанс, затем выход; таблицы `user_security`/`login_attempts` и функции `register_login_attempt`, `is_user_blocked` созданы, но `AuthService` их пока не вызывает | риск |
| Смена пароля | функции смены пароля в приложении нет | ограничение |
| MFA | отсутствует | ограничение учебного стенда |

**Пример хеша в БД:** `$2a$10$...` — bcrypt с солью; одинаковые пароли дают разные хеши. Демонстрационные записи из `02_seed.sql` созданы с прежней стоимостью 6 (`$2a$06$...`), новые учётные записи — со стоимостью 10.

**Рекомендации:**

1. минимальная длина 12 символов, проверка по словарю;
2. блокировка на 15 минут после 5 неудач, экспоненциальная задержка;
3. журналирование успешных и неуспешных входов;
4. смена пароля при первом входе для демонстрационных учётных записей;
5. при промышленной эксплуатации — MFA для администраторов.

## 5. Авторизация и права ролей

### 5.1. Фактические права

Данные получены из `information_schema` и проверены запросами в `psql`.

| Роль | Права | Комментарий |
|---|---|---|
| `sto_admin` | `ALL` на все таблицы и последовательности, включая `users`, `roles`, `order_status_log` | полный доступ, используется приложением |
| `sto_manager` | `SELECT/INSERT/UPDATE` на `clients`, `cars`; `SELECT` на `orders` и `UPDATE (status_id)`; `SELECT/INSERT/UPDATE` на `order_services`; `SELECT` на `services` через группу; `EXECUTE` на `create_order`, `add_service_to_order`, `close_order`, `calculate_order_total`, `get_client_orders` | создаёт заявки только через `create_order()`, дату закрытия ставит триггер |
| `sto_master` | `SELECT` на `orders`, `clients`, `cars`, `order_statuses`; `SELECT/INSERT` на `order_services`; `UPDATE (status_id)` на `orders`; `SELECT` на `services` через группу | меняет только статус, `closed_at` недоступен |
| `sto_client` | `SELECT` на `services` и `v_my_orders` | базовые таблицы недоступны |
| `sto_readonly_group` | `SELECT` на `services`, `order_statuses`, `masters` | наследуется manager и master |

Проверки (актуальные для текущей схемы):

```text
sto_client: SELECT count(*) FROM orders;
ERROR: permission denied for table orders

sto_client: SET app.client_id='1';
            SELECT order_id, car, status FROM v_my_orders;
order_id = 1, 4   -- только заявки Иванова

sto_manager: SELECT create_order(1, 1, NULL, 'проверка');
create_order = 7        -- разрешено через SECURITY DEFINER

sto_manager: INSERT INTO orders (client_id, car_id, status_id) VALUES (1, 1, 1);
ERROR: permission denied for table orders

sto_manager: UPDATE orders SET closed_at = now() WHERE id = 1;
ERROR: permission denied for table orders
```

### 5.2. Разграничение в приложении

Права ролей описаны в `model/Permission.java` и `model/RolePermissions.java`. Боковое меню строится по `Navigation.visibleFor(...)`, а операции дополнительно проверяются в `OrderService` (`listVisible`, `getOrderVisible`, `createOrder`, `addService`, `closeOrder`, `statusLog`). Для клиента `OrderService.listVisible` вызывает `OrderRepository.findSummariesByClientId(user.clientId())`, поэтому в интерфейс не попадают чужие заявки. Проверка повторяется при открытии карточки заявки по номеру — прямой переход к чужой заявке завершается `AccessDeniedException`.

### 5.3. Ранее выявленные проблемы и их статус

#### SEC-01. Клиент мог запросить заявки любого клиента — **устранено**

**Было.** Функция `get_client_orders(p_client_id)` принимала произвольный `client_id`, представление `v_order_total` показывало все заявки, а JavaFX выводил общий список.

**Что сделано.**

1. В `users` добавлено поле `client_id` с уникальным индексом; в seed-данных учётная запись `client` привязана к карточке Иванова.
2. Создано представление `v_my_orders`, которое фильтрует заявки по `current_setting('app.client_id', true)`.
3. `sto_client` получил `SELECT` только на `v_my_orders` и `services`; доступ к `orders`, `clients`, `cars` запрещён.
4. `OrderService` берёт `clientId` из аутентифицированного пользователя и не принимает его из ввода; консольное меню для клиента больше не спрашивает ID.
5. Добавлены тесты `clientAccountIsBoundToClientCard`, `clientSeesOnlyOwnOrders`, `clientCannotOpenForeignOrder`.

**Остаточный риск.** Приложение подключается под `sto_admin`, поэтому фильтрация в БД-представлении не является единственной линией защиты; окончательная проверка выполняется в сервисе.

**Классификация:** OWASP A01:2021 Broken Access Control, CWE-639, CWE-284.

#### SEC-02. Приложение работает под `sto_admin` (высокий риск)

**Описание.** `db.username=sto_admin`; роль имеет `ALL` на все таблицы, включая `users`, `roles`, `order_status_log`, и может удалять журнал.

**Следствие.** Любая ошибка в приложении или компрометация учётной записи приложения даёт полный контроль над данными. Ограничения `sto_manager`/`sto_master`/`sto_client` при этом не защищают, так как приложение подключается не под ними.

**Рекомендация.** Создать роль `sto_app` с минимальными правами: `SELECT/INSERT/UPDATE` на необходимые таблицы, `EXECUTE` на функции, без `DELETE` на журнал и без прав на `users/roles`; миграции выполнять отдельной ролью.

**Классификация:** OWASP A01/A05, CWE-250 (Execution with Unnecessary Privileges).

#### SEC-03. Прямое изменение `closed_at` в обход бизнес-правила — **устранено**

**Было.** `sto_manager` имел `UPDATE` на все колонки `orders`, `sto_master` — `UPDATE (status_id, closed_at)`; дату закрытия можно было менять напрямую.

**Что сделано.** Обеим ролям выдано только `UPDATE (status_id)` на `orders`. `closed_at` заполняет `trigger_set_closed_at` при переводе заявки в статус «завершена»; прямой `UPDATE orders SET closed_at = ...` завершается `permission denied for table orders`.

**Остаточный риск.** `sto_admin` по-прежнему может менять `closed_at` — это следствие SEC-02.

**Классификация:** OWASP A01, CWE-732 (Incorrect Permission Assignment for Critical Resource).

#### SEC-04. Секреты в репозитории (средний риск)

**Описание.** `application.properties` содержит `db.password=admin_pass`; `sto.sql` — пароли ролей; `docker-compose.yml` — `postgres/postgres` по умолчанию.

**Следствие.** При публикации репозитория секреты становятся известны; пароли не ротируются.

**Рекомендация.** Использовать `STO_DB_PASSWORD`, `.env` вне Git, vault/secret manager; разные пароли для стендов; ротация; проверка истории Git на утечки.

**Классификация:** OWASP A02/A05, CWE-798 (Use of Hard-coded Credentials), CWE-522.

#### SEC-05. Нет TLS при подключении к БД (средний риск)

**Описание.** JDBC URL не содержит `sslmode`; трафик между приложением и PostgreSQL не шифруется.

**Следствие.** В локальной сети возможен перехват учётных данных и данных клиентов.

**Рекомендация.** Включить TLS на PostgreSQL, использовать `sslmode=verify-full` и доверенный сертификат; ограничить сеть Docker.

**Классификация:** OWASP A02, CWE-319 (Cleartext Transmission of Sensitive Information).

#### SEC-06. Нет защиты от подбора пароля (средний риск)

**Описание.** В консоли и JavaFX 3 попытки на сеанс, затем выход. Перезапуск приложения снова даёт попытки; задержки и автоматической блокировки нет. В `sto.sql` уже созданы таблицы `user_security`, `login_attempts` и функции `register_login_attempt`, `is_user_blocked`, `unblock_expired_users`, но `AuthService` их не вызывает — сделано намеренно, чтобы демонстрационные учётные записи не блокировались во время тестирования.

**Рекомендация.** Вызывать `register_login_attempt` при каждом входе, проверять `is_user_blocked` перед проверкой пароля, включить снятие истёкших блокировок; для внешнего интерфейса добавить CAPTCHA и оповещение администратора.

**Классификация:** OWASP A07, CWE-307 (Improper Restriction of Excessive Authentication Attempts).

#### SEC-07. Слабый аудит действий (средний риск)

**Описание.** `order_status_log.changed_by` по умолчанию равен `current_user`, то есть `sto_admin` для всех действий приложения. Реальный пользователь (`manager`/`master`) в журнале не виден. `sto_admin` может удалять/изменять журнал.

**Следствие.** Нельзя доказать, кто именно изменил статус; журнал не является доверенным.

**Рекомендация.** Передавать идентификатор пользователя через `SET LOCAL app.user_id` и писать его в триггере; запретить `UPDATE/DELETE` на `order_status_log`; хранить журнал в отдельной схеме/таблице с ограниченным доступом.

**Классификация:** OWASP A09, CWE-778 (Insufficient Logging), CWE-732.

#### SEC-08. Порт PostgreSQL опубликован на все интерфейсы (средний риск)

**Описание.** `docker ps` показывает `0.0.0.0:5434->5432/tcp`; суперпользователь `postgres` доступен с паролем `postgres`.

**Следствие.** В незащищённой сети возможен прямой доступ к БД.

**Рекомендация.** Привязать порт к `127.0.0.1`, задать сложный пароль, не публиковать БД в интернет, использовать внутреннюю Docker-сеть.

**Классификация:** OWASP A05, CWE-1327/CWE-1188.

#### SEC-09. Нет таймаута запроса (низкий/средний риск)

**Описание.** `statement_timeout` не задан; долгий запрос удерживает соединение пула.

**Рекомендация.** Установить `statement_timeout` и `idle_in_transaction_session_timeout` на уровне роли/БД; ограничить время удержания соединения.

**Классификация:** OWASP A05, CWE-400 (Uncontrolled Resource Consumption).

#### SEC-10. Детали SQL в сообщении об ошибке (низкий риск)

**Описание.** Сообщение содержит SQLState, имя операции и до 300 символов текста PostgreSQL.

**Следствие.** Для локального администратора это полезно; для внешнего пользователя — избыточно.

**Рекомендация.** Разделить сообщения: пользователю — краткий текст, в журнал — детали; не показывать SQL в промышленном UI.

**Классификация:** OWASP A09/A04, CWE-209 (Generation of Error Message Containing Sensitive Information).

## 7. Валидация входных данных

| Поле | Проверка в Java | Проверка в БД |
|---|---|---|
| ФИО клиента | не пусто, ≤ 150 | `NOT NULL`, `VARCHAR(150)` |
| Телефон | regex `\+?[0-9()\-\s]{5,20}`, ≤ 20 | `UNIQUE`, `VARCHAR(20)` |
| E-mail | содержит `@`, ≤ 100 | `VARCHAR(100)` |
| Марка/модель | не пусто, ≤ 50 | `VARCHAR(50)` |
| Год | 1950..2100 | `CHECK (year BETWEEN 1950 AND 2100)` |
| Госномер | не пусто, ≤ 15 | `UNIQUE`, `VARCHAR(15)` |
| VIN | ≤ 17 | `VARCHAR(17)` |
| Цена услуги | не `NULL`, ≥ 0 | `CHECK (price >= 0)` |
| Длительность | > 0 | `CHECK (duration_min > 0)` |
| Количество | 1..100 | `CHECK (quantity > 0)` |
| Описание | не пусто, ≤ 2000 | `TEXT` |
| Статус заявки | закрытые статусы проверяются по имени | триггер `trigger_check_order_status` |

**Принцип:** валидация в Java даёт понятное сообщение, ограничения в БД защищают от обхода. Это подтверждено негативными тестами TC-14, TC-17, TC-18, TC-19.

## 12. Вывод

Базовая защита модуля выполнена корректно: SQL-инъекции не проходят, пароли хранятся в bcrypt, параметры подключения не содержат пароля в журнале, роли БД разделены, ограничения целостности дублируются на уровне PostgreSQL. В текущей версии устранены горизонтальный доступ клиента к чужим заявкам (SEC-01) и возможность прямого изменения `closed_at` (SEC-03): клиент привязан к карточке через `users.client_id`, заявки фильтруются в сервисе и представлении `v_my_orders`, а ролям manager/master разрешено менять только `status_id`. Остаются риски, связанные с подключением приложения под `sto_admin` (SEC-02), секретами в репозитории (SEC-04), отсутствием TLS (SEC-05), не задействованной блокировкой входов (SEC-06), аудитом (SEC-07), сетевым доступом к БД (SEC-08) и таймаутами (SEC-09). Они классифицированы по OWASP/CWE и включены в план устранения; для учебного стенда допустимы при условии документирования и выполнения первоочередных мер перед реальным запуском.
