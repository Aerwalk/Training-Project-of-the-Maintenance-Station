## 2. Что и как тестировалось

### 2.1. Объём

* конфигурация подключения и переопределение переменными окружения;
* пул соединений, проверка валидности, транзакции, retry;
* все репозитории и сервисы;
* представление `v_order_total`, функции `create_order`, `add_service_to_order`, `close_order`, `calculate_order_total`, `get_client_orders`;
* триггеры `trigger_set_closed_at`, `trigger_log_status_change`, `trigger_check_order_status`;
* ограничения `NOT NULL`, `UNIQUE`, `CHECK`, внешние ключи;
* права ролей `sto_admin`, `sto_manager`, `sto_master`, `sto_client`, `sto_readonly_group`;
* консольный интерфейс, demo-сценарий, `--check`, `--list-orders`, веб-режим `--web` (REST API + Angular);
* поведение при недоступной БД, неверном пароле, таймауте, конкуренции, `statement_timeout`.

## 4. Анализ причин ошибок

### 4.1. По типам

| Тип | Кол-во | Примеры | Что показал анализ |
|---|---:|---|---|
| Синтаксические / DDL | 1 | D-01 | ошибки порядка объектов не видны при чтении кода; нужен прогон на чистой БД |
| Компиляции Java | 2 | D-02, D-03 | lambda требует effectively final; невнимательность к сигнатуре метода |
| Логические | 3 | D-04, D-06, D-07 | неверный порядок операций, потеря `NULL`, обход инварианта |
| Runtime / среда | 1 | D-05 | кодировка консоли зависит от ОС и терминала |
| Данные / тестовые | — | demo-заявки | тестовые данные влияют на counts, но не на корректность |

### 4.2. Корневые причины

1. **Проверка только на уже развёрнутой БД.** D-01 проявился лишь на чистом томе. Мера: обязательный прогон `docker compose down -v && up -d` перед сдачей.
2. **Отсутствие теста на порядок операций.** D-04 не ловился автотестами, потому что тестировался успешный сценарий. Мера: тест/ручной кейс «БД недоступна».
3. **Недооценка платформенных различий.** D-05 связан с кодировкой Windows. Мера: принудительный UTF-8 и проверка вывода.
4. **Ручные изменения в обход приложения.** D-07 возник из прямого `UPDATE`. Мера: закрытие только через функцию, триггер на инвариант.
5. **Слабая диагностика конфигурации.** RS-06 показал, что неверный пароль маскируется таймаутом. Мера: разбор причины Hikari, отдельная проверка учётных данных.
6. **Тестовые данные не изолированы от демонстрационных.** Demo создаёт заявки в той же БД. Мера: очистка/отдельная схема для тестов.

### 4.3. Почему ошибки не были обнаружены раньше

| Ошибка | Почему пропущена | Что изменить в процессе |
|---|---|---|
| D-01 | проверяли на уже инициализированной БД | добавить clean-db smoke в Definition of Done |
| D-04 | тестировали только успешный путь | обязательный негативный кейс для каждой команды |
| D-05 | смотрели вывод в IDE, а не в Windows-консоли | проверять целевые терминалы |
| D-06 | не было заявки без мастера в ручном сценарии | добавить граничные данные в seed/тесты |
| D-07 | инвариант не был сформулирован явно | описать инварианты и проверять их SQL-запросами |

## 8. Рекомендации

### 8.1. Первоочередные

1. закрыть SEC-01: связать пользователя с клиентом и запретить произвольный `client_id`;
2. перейти на роль `sto_app` с минимальными правами;
3. отозвать `UPDATE (closed_at)` и разрешить закрытие только через `close_order`;
4. вынести секреты из репозитория, сменить демонстрационные пароли;
5. привязать порт БД к `127.0.0.1`.

### 8.2. Среднесрочные

6. включить TLS и `sslmode=verify-full`;
7. настроить `statement_timeout`, `idle_in_transaction_session_timeout`;
8. сделать журнал статусов append-only и писать реального пользователя;
9. добавить блокировку после неудачных входов и журнал аутентификации;
10. добавить индекс `order_services(order_id)` и проверить планы на данных, близких к реальным;
11. автоматизировать RS-04 (pool exhaustion) и RS-10 (ограничение диска/сети).

### 8.3. Процессные

12. включить clean-db smoke в Definition of Done;
13. для каждой команды/флага иметь негативный кейс;
14. проводить SCA и обзор прав ролей перед каждым релизом;
15. хранить тестовые данные отдельно от демонстрационных.

## 9. Заключение

Проведённое тестирование подтвердило работоспособность модуля доступа к БД СТО: 37 автоматических тестов проходят, 20 функциональных кейсов выполнены, ключевые бизнес-правила защищены на уровне PostgreSQL. В ходе работы найдено и исправлено 7 дефектов, включая блокирующую ошибку инициализации схемы и логическую ошибку вывода `--check`. Классификация по OWASP Top 10 и CWE показала, что критических уязвимостей SQL-инъекций нет, но для промышленной эксплуатации необходимо устранить риски управления доступом, привилегий, секретов и транспорта. Остаточные риски и невыполненные сценарии зафиксированы честно; план устранения приоритизирован. Модуль готов к демонстрации и защите практики.
