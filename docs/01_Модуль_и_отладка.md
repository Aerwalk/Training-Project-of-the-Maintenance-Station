# Тема 1. Отладка программных модулей

## 1.1. Цель и содержание работ

**Цель:** разработать модуль доступа к базе данных для приложения СТО, выполнить его отладку, разобрать типовые ошибки и обеспечить устойчивость к сбоям.

**Состав работ по теме:**

* задание 1 — создать модуль доступа к БД;
* задание 2 — разобрать синтаксические, логические и runtime-ошибки, подготовить описание модуля и список ожидаемых ошибок;
* задание 3 — добавить обработку исключений и механизм повторных попыток, проверить работу.

## 1.2. Архитектура модуля

Приложение построено по слоистой схеме. Зависимости направлены «сверху вниз»: интерфейс не работает с JDBC напрямую, а слой сервисов не знает о деталях SQL.

```
┌──────────────────────────────────────────────────────────────┐
│ CLI: StoApplication, ConsoleMenu, DemoRunner                 │
│ ввод/вывод, ролевое меню, демонстрационный сценарий          │
└───────────────────────────┬──────────────────────────────────┘
                            │ вызовы use-case
┌───────────────────────────▼──────────────────────────────────┐
│ Service: AuthService, CatalogService, OrderService           │
│ бизнес-правила, валидация входных данных                     │
└───────────────────────────┬──────────────────────────────────┘
                            │ типизированные методы
┌───────────────────────────▼──────────────────────────────────┐
│ Repository: User, Client, Car, Master, Service, Order        │
│ SQL, PreparedStatement/CallableStatement, маппинг ResultSet  │
└───────────────────────────┬──────────────────────────────────┘
                            │ Connection
┌───────────────────────────▼──────────────────────────────────┐
│ DB: ConnectionManager, RetryPolicy, SqlExceptionTranslator    │
│ HikariCP, транзакции, retry, трансляция SQLException         │
└───────────────────────────┬──────────────────────────────────┘
                            │ JDBC
┌───────────────────────────▼──────────────────────────────────┐
│ PostgreSQL 16 (Docker): таблицы, view, функции, триггеры      │
└──────────────────────────────────────────────────────────────┘
```

### Классы модуля

| Класс | Назначение |
|---|---|
| `AppConfig` | чтение `application.properties`, `-Dconfig.file`, переменных окружения |
| `DbSettings` | неизменяемый набор параметров подключения и пула |
| `ConnectionManager` | пул HikariCP, выдача соединения, `withConnection`, `inTransaction`, `ping` |
| `RetryPolicy` | расчёт задержки, классификация временных сбоев, sleep между попытками |
| `SqlExceptionTranslator` | преобразование `SQLException` в предметные исключения по SQLState |
| `UserRepository`, `ClientRepository`, `CarRepository`, `MasterRepository`, `ServiceRepository`, `OrderRepository` | JDBC-доступ к таблицам и функциям |
| `AuthService` | аутентификация, проверка пароля через `crypt()` |
| `CatalogService` | справочники, валидация клиентов, автомобилей и услуг |
| `OrderService` | создание заявки, добавление услуг, закрытие, расчёт стоимости, журнал |
| `ConsoleMenu` | интерактивное меню, обработка ошибок, ролевые ограничения |
| `DemoRunner` | автоматический сквозной сценарий для демонстрации и проверки |

### Принципы реализации

1. **Параметризованные запросы.** Все значения передаются через `PreparedStatement`/`CallableStatement`; конкатенация пользовательских данных в SQL отсутствует. Это исключает SQL-инъекции.
2. **Пул соединений.** HikariCP ограничивает число соединений, проверяет их валидность и переиспользует. Параметры пула заданы в properties.
3. **Транзакции.** Метод `ConnectionManager.inTransaction` выключает autoCommit, фиксирует результат и откатывает изменения при любом исключении.
4. **Предметные исключения.** Прикладной код не зависит от `SQLException`: он получает `DuplicateKeyException`, `ForeignKeyViolationException`, `ConnectionUnavailableException` и т.п.
5. **Бизнес-правила на стороне БД.** Ограничения `NOT NULL`, `UNIQUE`, `CHECK`, внешние ключи, триггеры и хранимые функции защищают данные даже при обращении в обход приложения.
6. **Секреты не в коде.** Параметры подключения находятся в properties и могут быть переопределены переменными окружения.

База создана скриптом [`sto.sql`](../sto.sql), демонстрационные данные — [`docker/init/02_seed.sql`](../docker/init/02_seed.sql).

| `calculate_order_total` | функция | расчёт стоимости заявки |

| `trg_log_status_change` | триггер | запись в `order_status_log` |
| `trg_check_order_status` | триггер | запрет добавления услуг в завершённую/отменённую заявку |

### Роли и права

В `sto.sql` созданы роли `sto_admin`, `sto_manager`, `sto_master`, `sto_client` и группа `sto_readonly_group`.

* `sto_admin` — полный доступ к таблицам и последовательностям;
* `sto_manager` — чтение/изменение клиентов, автомобилей, заявок и услуг в заявках; чтение справочников;
* `sto_master` — чтение заявок, клиентов, автомобилей, услуг; добавление услуг; обновление `status_id` и `closed_at`;
* `sto_client` — только чтение представления `v_order_total`;
* `sto_manager` и `sto_master` наследуют права `sto_readonly_group` (чтение `services`, `order_statuses`, `masters`).

## 1.4. Задание 1. Модуль доступа к БД

Модуль реализован в пакетах:

* `org.example.sto.db` — инфраструктура доступа к данным;
* `org.example.sto.repository` — SQL-запросы и маппинг;
* `org.example.sto.service` — бизнес-логика;
* `org.example.sto.model` — record-модели;
* `org.example.sto.cli` — консольный интерфейс.

### Параметры подключения

Файл `src/main/resources/application.properties`:

```properties
db.url=jdbc:postgresql://localhost:5434/sto
db.username=sto_admin
db.password=admin_pass
db.pool.maximumPoolSize=5
db.pool.connectionTimeoutMs=3000
db.retry.maxAttempts=4
db.retry.initialDelayMs=250
db.retry.multiplier=2.0
db.retry.maxDelayMs=4000
```

`AppConfig` поддерживает внешний файл (`-Dconfig.file=...`) и переменные окружения `STO_DB_URL`, `STO_DB_USERNAME`, `STO_DB_PASSWORD`, `STO_DB_MAX_POOL_SIZE`, `STO_DB_RETRY_MAX_ATTEMPTS`. Пароль не выводится в журнал: для логирования используется `DbSettings.toSafeString()`.

### Пример работы с соединением

```java
public <T> T withConnection(String operation, SqlWork<T> work) {
    try (Connection connection = getConnection()) {
        return work.apply(connection);
    } catch (SQLException e) {
        throw SqlExceptionTranslator.translate(e, operation);
    }
}
```

### Пример вызова хранимой функции

```java
public int createOrder(int clientId, int carId, Integer masterId, String description) {
    return connectionManager.withConnection("orders.createOrder", connection -> {
        String sql = "{? = call create_order(?, ?, ?, ?)}";
        try (CallableStatement statement = connection.prepareCall(sql)) {
            statement.registerOutParameter(1, Types.INTEGER);
            statement.setInt(2, clientId);
            statement.setInt(3, carId);
            if (masterId == null) {
                statement.setNull(4, Types.INTEGER);
            } else {
                statement.setInt(4, masterId);
            }
            statement.setString(5, description);
            statement.execute();
            return statement.getInt(1);
        }
    });
}
```

Использование `CallableStatement` и `setNull` важно: `master_id` в схеме допускает `NULL`, поэтому заявка может быть создана без назначенного мастера.

## 1.5. Задание 2. Ошибки трёх типов

Подробный разбор приведён в отдельном файле [`expected-errors.md`](expected-errors.md). Ниже — сводка.

| Тип ошибки | Суть | Пример в проекте | Обнаружение | Обработка |
|---|---|---|---|---|
| Синтаксическая | неверный SQL, опечатка, несуществующий объект, неверная сигнатура функции | блок `GRANT EXECUTE ON FUNCTION create_order(...)` стоял до создания функции; PostgreSQL выдал `42883 function ... does not exist` | SQLState 42xxx, сообщение PostgreSQL, журнал инициализации контейнера | исправление порядка DDL; трансляция в `QueryException` |
| Логическая | запрос синтаксически верен, но возвращает неверные данные | JOIN заявки с автомобилем по `client_id` вместо `car_id`; отсутствие `GROUP BY`; добавление услуги в закрытую заявку | сверка с эталонными суммами, тесты на известных данных, `EXPLAIN`, анализ бизнес-правил | исправление условия JOIN; агрегация; проверки в сервисе + триггер в БД |
| Runtime | сбой во время выполнения: нет соединения, таймаут, нарушение ограничений, блокировка | остановленный контейнер PostgreSQL; дубликат телефона; `NULL` в `NOT NULL`; превышение `VARCHAR(20)`; нарушение FK | SQLState 08xxx/23xxx/22xxx, `SQLException`, журнал приложения | retry для 08xxx, предметные исключения для 23xxx/22xxx, сообщение пользователю |

### Ошибка, найденная при запуске стенда

Исходный `sto.sql` содержал блок:

```sql
GRANT EXECUTE ON FUNCTION create_order(INTEGER, INTEGER, INTEGER, TEXT) TO sto_manager;
...
-- функции объявлены ниже
CREATE OR REPLACE FUNCTION create_order(...)
```

При инициализации Docker PostgreSQL выполняет файлы с `ON_ERROR_STOP=1`, поэтому контейнер завершал init с ошибкой:

```
ERROR:  function create_order(integer, integer, integer, text) does not exist
```

**Исправление:** блок `GRANT EXECUTE` перенесён после создания всех функций. Схема и бизнес-правила не изменялись. Это пример синтаксической/объектной ошибки, проявившейся только при развёртывании, а не при чтении кода.

### Логическая ошибка, предотвращённая тестами

При расчёте стоимости нельзя соединять `orders` и `cars` только по клиенту:

```sql
-- неверно: у клиента может быть несколько автомобилей, сумма размножится
JOIN cars cr ON cr.client_id = o.client_id
```

Правильное условие — по конкретному автомобилю заявки:

```sql
JOIN cars cr ON cr.id = o.car_id
```

В представлении `v_order_total` используется корректное соединение. Тест `viewTotalEqualsStoredFunctionResult` сверяет сумму представления с результатом `calculate_order_total`, что позволяет обнаружить подобное размножение строк.

## 1.6. Задание 3. Обработка исключений и повторные попытки

### Иерархия исключений

```
RuntimeException
└── DatabaseException
    ├── ConnectionUnavailableException
    │   └── RetryExhaustedException
    ├── DataIntegrityException
    │   ├── DuplicateKeyException
    │   └── ForeignKeyViolationException
    ├── QueryException
    └── TransientDatabaseException
```

Отдельно определены `ValidationException` и `EntityNotFoundException` — ошибки бизнес-уровня, не связанные с JDBC.

### Трансляция SQLState

`SqlExceptionTranslator` анализирует SQLState, включая цепочку `getNextException()`:

| SQLState | Исключение | Причина |
|---|---|---|
| `23505` | `DuplicateKeyException` | нарушение UNIQUE |
| `23503` | `ForeignKeyViolationException` | нарушение внешнего ключа |
| `23502` | `DataIntegrityException` | NULL в NOT NULL |
| `23514` | `DataIntegrityException` | нарушение CHECK |
| `22001` | `DataIntegrityException` | превышение длины VARCHAR |
| `08xxx`, `57P03` | `ConnectionUnavailableException` | потеря/недоступность соединения |
| `28xxx` | `ConnectionUnavailableException` | ошибка аутентификации |
| `42xxx` | `QueryException` | синтаксис SQL, несуществующий объект |
| `40001`, `40P01` | `TransientDatabaseException` | сериализация, deadlock |
| остальные | `DatabaseException` | прочие ошибки |

### Механизм retry

`RetryPolicy` повторяет только временные сбои: SQLState `08xxx`, `57P03`, `40001`, `40P01`, а также `SQLTransientConnectionException`, `SQLRecoverableException`, `ConnectException`, `SocketException`, `SocketTimeoutException`.

Задержка рассчитывается по формуле:

```
delay(n) = min(maxDelay, initialDelay * multiplier^(n-1))
```

При настройках по умолчанию: 250 мс, 500 мс, 1000 мс между попытками; всего 4 попытки. Ошибки целостности и синтаксиса не повторяются, чтобы не маскировать дефекты данных.

Ключевой фрагмент:

```java
for (int attempt = 1; attempt <= attempts; attempt++) {
    try {
        Connection connection = dataSource.getConnection();
        if (isValid(connection)) {
            return connection;
        }
    } catch (SQLException e) {
        lastError = e;
    }
    if (attempt == attempts || !RetryPolicy.isRetryable(lastError)) {
        break;
    }
    retryPolicy.sleepBeforeRetry(attempt);
}
throw new RetryExhaustedException("Не удалось подключиться к БД...", attempts, lastError);
```

### Проверка retry при остановленной БД

Сценарий: контейнер остановлен, приложение запущено с `--check`.


### Транзакции

`ConnectionManager.inTransaction`:

```java
connection.setAutoCommit(false);
try {
    T result = work.apply(connection);
    connection.commit();
    return result;
} catch (SQLException e) {
    rollbackQuietly(connection, e);
    throw SqlExceptionTranslator.translate(e, operation);
} catch (RuntimeException | Error e) {
    rollbackQuietly(connection, e);
    throw e;
} finally {
    connection.setAutoCommit(previousAutoCommit);
    closeQuietly(connection);
}
```

Тест `transactionRollsBackOnRuntimeException` вставляет клиента, затем искусственно выбрасывает исключение и проверяет, что запись откатилась.

## 1.7. Отладка: найденные и устранённые дефекты

| № | Дефект | Проявление | Причина | Исправление |
|---|---|---|---|---|
| 1 | `GRANT EXECUTE` до создания функций | init-контейнер завершался с `42883` | неверный порядок DDL в `sto.sql` | блок прав перенесён после функций |
| 2 | Локальная переменная в lambda | ошибка компиляции «local variables referenced from a lambda expression must be final» | переменная `passwordText` переприсваивалась | введена финальная копия, исходный `char[]` очищается в `finally` |
| 3 | Неверный вызов `hasArg` | ошибка компиляции | пропущен аргумент `args` | вызов приведён к `hasArg(args, "-h")` |
| 4 | `--check` печатал «Подключение успешно» до проверки | при остановленной БД сначала выводился успех, затем ошибка | порядок операций | сначала `ping()`, затем вывод результата |
| 5 | Кириллица в консоли Windows | вывод в CP1251/CP866, отчёт нечитаем; отдельно ломалось приглашение «Пароль:» | кодировка stdout JVM; `readPassword` пишет напрямую в консоль в кодировке ОС | `System.setOut`/`setErr` с `StandardCharsets.UTF_8`; приглашение печатается через `PrintStream`, затем вызывается `readPassword()` |
| 6 | `NULL` в `master_id` и `closed_at` | возможный `NullPointerException`/неверный маппинг | примитивные типы | `wasNull()` и `Integer`/`LocalDateTime` |
| 7 | `closed_at` у новой заявки после ручного UPDATE | нарушение инварианта «закрыто только завершённое» | прямой UPDATE в обход триггера | сброшено значение; в приложении статус меняется только через `close_order`/проверку |

## 1.8. Вывод по теме

Модуль доступа к БД реализован и отлажен. Обработка исключений разделяет ошибки данных, SQL и соединения; retry применяется только к временным сбоям. Транзакции гарантируют атомарность. Найденные при отладке дефекты устранены, их причины и решения зафиксированы в отчёте. Подробный список ожидаемых ошибок вынесен в [`expected-errors.md`](expected-errors.md).
