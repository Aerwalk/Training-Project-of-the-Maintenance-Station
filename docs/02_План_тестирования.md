# План тестирования модуля доступа к БД СТО

**Документ:** план тестирования (задание 4)  
**Объект:** Maven-проект `sto-db-module`, модуль доступа к PostgreSQL для приложения СТО  
**Версия:** 1.0  
**Связанные документы:** [Техническое задание](07_Техническое_задание.md), [Тест-кейсы](03_Тест-кейсы.md), [Результаты тестирования](04_Результаты_тестирования.md)

## 1. Цель тестирования

Подтвердить, что модуль доступа к БД:

1. корректно выполняет все заявленные операции с данными СТО;
2. соблюдает бизнес-правила, реализованные как в Java, так и в PostgreSQL;
3. устойчиво обрабатывает ошибки данных, SQL и соединения;
4. не создаёт условий для SQL-инъекций и обхода прав ролей;
5. обеспечивает приемлемое время выполнения типовых запросов и читаемость SQL-кода.

Цель не ограничивается поиском ошибок: по результатам тестирования должно быть принято обоснованное решение о готовности модуля к демонстрации и передаче.

## 2. Объект и границы тестирования

### 2.1. Что входит в объект

| Компонент | Проверяемые возможности |
|---|---|
| `config` | чтение `application.properties`, переопределение переменными окружения, валидация параметров, сокрытие пароля |
| `db` | пул HikariCP, выдача соединения, `isValid`, транзакции, retry, трансляция `SQLException` |
| `repository` | параметризованные SELECT/INSERT/UPDATE, вызовы функций, маппинг `ResultSet`, обработка `NULL` |
| `service` | валидация клиентов, автомобилей, услуг, заявок; проверка прав и статусов |
| `cli` | вход, ролевое меню, вывод таблиц, обработка ошибок, demo-сценарий |
| PostgreSQL | схема, ограничения, представление `v_order_total`, функции, триггеры, роли и права |
| Docker | автоматическая инициализация схемы и seed-данных на чистом томе |

### 2.2. Что не входит в объект

* веб-интерфейс и REST API — приложение консольное;
* нагрузочное тестирование промышленного уровня (сотни одновременных пользователей);
* проверка восстановления после отказа диска и потери сетевого сегмента;
* тестирование чужого приложения: по заданию 7 предусмотрен обмен результатами, но фактический peer-app в рамках практики отсутствовал; это ограничение зафиксировано в [отчёте о тестировании](06_Отчет_о_тестировании.md);
* юридическая экспертиза и сертификация.

## 3. Виды тестирования и обоснование выбора

Выбрана риск-ориентированная стратегия: сначала проверяются места, где ошибка приводит к неверным деньгам, потере данных или обходу прав.

| Вид | Цель | Что проверяется | Инструмент | Когда выполняется |
|---|---|---|---|---|
| Модульное | проверить изолированную логику без БД | retry, трансляция SQLState, валидация, конфигурация | JUnit 5 | при каждой сборке |
| Интеграционное | проверить связку Java ↔ PostgreSQL | репозитории, функции, триггеры, ограничения, роли | JUnit 5 + реальный Docker-стенд | при каждой сборке (если БД доступна) |
| Функциональное | проверить сценарии пользователя | вход, заявки, услуги, закрытие, отчёты | ручные кейсы + CLI + demo | после стабилизации сборки |
| Нефункциональное | проверить производительность, читаемость, надёжность, переносимость | план запросов, стиль SQL, retry, кодировка | `EXPLAIN ANALYZE`, чек-лист, логи | после функционального |
| Регрессионное | убедиться, что исправления не сломали ранее работающее | весь набор автотестов + ключевые ручные кейсы | JUnit 5, `--demo` | после каждого дефекта |
| Тестирование безопасности | проверить инъекции, пароли, права | вход, SQL-инъекции, роли БД, секреты | ручные атаки + psql | параллельно с функциональным |

### 3.1. Почему выбраны именно эти виды

* **Модульные тесты** дешевы и быстро локализуют ошибку. Они обязательны для retry и трансляции SQLState: эти правила легко проверить без реальной БД.
* **Интеграционные тесты** необходимы, потому что часть бизнес-правил живёт в PostgreSQL (триггеры, функции, ограничения). Mock-объекты не обнаружили бы, например, неверный `JOIN` или порядок DDL.
* **Функциональные тесты** проверяют не методы, а результат для пользователя: создана ли заявка, совпала ли сумма, закрылась ли она.
* **Нефункциональные тесты** важны для учебного модуля: запрос с `Seq Scan` на демо-данных работает, но на росте данных деградирует; нечитаемый SQL сложно сопровождать.
* **Регрессионные тесты** нужны после каждого исправления, так как изменения в `sto.sql` влияют сразу на все сценарии.

## 4. Стратегия и уровни

Применяется пирамида тестирования:

```
        ┌──────────────────────────┐
        │ Ручные функциональные    │  20 кейсов TC-01…TC-20
        │ и сценарии устойчивости  │  10 кейсов RS-01…RS-10
        ├──────────────────────────┤
        │ Интеграционные           │  16 тестов (Java + PostgreSQL)
        ├──────────────────────────┤
        │ Модульные                │  21 тест (retry, SQLState, validation, config)
        └──────────────────────────┘
```

Дополнительно выполняется **smoke-тест** `--demo`: он проходит полный бизнес-цикл и используется как быстрый признак работоспособности стенда.

### 4.1. Подход к тестовым данным

* используется отдельная БД `sto` в Docker, а не рабочая база;
* схема и seed-данные создаются автоматически из `sto.sql` и `docker/init/02_seed.sql`;
* тесты, изменяющие данные, создают собственные записи с уникальными телефонами/номерами и удаляют их в `finally`;
* для проверки ограничений применяются заведомо некорректные значения (длина > 20, год 1800, несуществующий клиент);
* перед ответственным прогоном рекомендуется пересоздать стенд: `docker compose down -v && docker compose up -d`.

## 6. Критерии входа и выхода

### 6.1. Критерии входа (начало тестирования)

* контейнер `sto-postgres` находится в состоянии `healthy`;
* `sto.sql` и seed-скрипт применились без ошибок;
* проект собирается командой `mvn package`;
* известны тестовые учётные записи и эталонные данные.

### 6.2. Критерии выхода (завершение тестирования)

* все 37 автоматических тестов проходят, пропусков по причине недоступности БД нет;
* все 20 функциональных кейсов имеют результат «Пройден» либо документированное отклонение;
* для каждого дефекта зафиксированы причина, исправление и регрессионный тест;
* критические и высокие дефекты закрыты; остаточные риски перечислены;
* `--check` и `--demo` завершаются успешно;
* результаты и доказательства приложены в `docs/evidence/`.

## 8. Сценарии по уровням

Ниже — по два примера на каждый уровень. Полные наборы приведены в [03_Тест-кейсы.md](03_Тест-кейсы.md).

### 8.1. Модульный уровень

**Сценарий ML-1. Экспоненциальная задержка retry.**
Вход: `RetryPolicy(4, 250, 2.0, 4000)`. Действие: вычислить задержку после 1–5 неудачных попыток. Ожидание: 250, 500, 1000, 2000, 4000 мс (с ограничением сверху).

**Сценарий ML-2. Трансляция нарушения UNIQUE.**
Вход: `SQLException` с SQLState `23505`. Действие: вызвать `SqlExceptionTranslator.translate`. Ожидание: `DuplicateKeyException`, SQLState сохранён, операция сохранена.

### 8.2. Интеграционный уровень

**Сценарий IL-1. Сумма представления равна функции.**
Действие: выбрать заявку с ненулевой стоимостью, сравнить `v_order_total.total_cost` и `calculate_order_total(order_id)`. Ожидание: значения равны.

**Сценарий IL-2. Запрет услуги в завершённой заявке.**
Предусловие: существует заявка со статусом «завершена». Действие: вызвать `OrderService.addService`. Ожидание: `ValidationException`, данные не изменены; при обходе сервиса срабатывает триггер БД.

### 8.3. Функциональный уровень

**Сценарий FL-1. Полный цикл заявки.**
Действие: войти как `manager`, создать заявку для клиента и его автомобиля, добавить две услуги, рассчитать стоимость, закрыть заявку, открыть журнал. Ожидание: заявка создана, сумма равна сумме услуг, статус «завершена», `closed_at` заполнен, в журнале есть запись о смене статуса.

**Сценарий FL-2. Негативный вход.**
Действие: ввести логин `admin` и неверный пароль, затем строку `' OR '1'='1`. Ожидание: вход не выполнен, выводится «Неверный логин или пароль», приложение не падает.

### 8.4. Нефункциональный уровень

**Сценарий NF-1. План запроса отчёта.**
Действие: выполнить `EXPLAIN (ANALYZE, BUFFERS)` для запроса по `v_order_total` и агрегирующего отчёта. Ожидание: план строится, время выполнения на демо-данных < 50 мс, используются индексы или обоснованные `Seq Scan` на малых таблицах.

**Сценарий NF-2. Поведение при недоступной БД.**
Действие: остановить контейнер, запустить `--check`. Ожидание: 4 попытки с задержками 250/500/1000 мс, понятное сообщение, код возврата 1, отсутствие необработанного стектрейса.

## 9. Регламент работы с дефектами

| Уровень | Определение | Пример | Реакция |
|---|---|---|---|
| Блокирующий | работа невозможна, данные теряются | init-скрипт не выполняется, приложение не подключается | исправить немедленно |
| Критический | неверные деньги/статус, обход прав | сумма заявки считается неверно, клиент видит чужие данные | исправить до завершения |
| Высокий | сценарий не выполняется, но есть обход | нельзя закрыть заявку | исправить в текущей итерации |
| Средний | неудобство, неверное сообщение | неверный текст ошибки, «кракозябры» | исправить при наличии времени |
| Низкий | косметика | выравнивание таблицы | занести в backlog |

Каждый дефект фиксируется по шаблону: **ID → шаги → фактический результат → ожидаемый результат → причина → исправление → регрессионный тест**. Фактические дефекты сведены в [06_Отчет_о_тестировании.md](06_Отчет_о_тестировании.md).

## 10. Риски планирования

| Риск | Влияние | Меры |
|---|---|---|
| Docker/PostgreSQL не запущен | интеграционные тесты пропускаются | проверка `docker compose ps`, assumption в тестах |
| Остаточные данные от прошлых прогонов | ложные результаты | уникальные тестовые значения, очистка в `finally`, пересоздание тома |
| Различие кодировок консоли | нечитаемый вывод | принудительный UTF-8 в `StoApplication` |
| Ограниченное время практики | часть сценариев устойчивости не выполняется | приоритизация, честная фиксация статусов и рекомендаций |
| Секреты в репозитории | риск утечки | переменные окружения, рекомендации по vault |

## 12. Вывод

План охватывает все уровни, необходимые для учебного модуля доступа к БД: от быстрых модульных проверок до ручных сценариев и анализа планов запросов. Особое внимание уделено деньгам (стоимость заявки), целостности (триггеры и ограничения), безопасности (инъекции и права ролей) и устойчивости (retry, транзакции). Критерии выхода сформулированы так, чтобы результат можно было проверить, а не оценить субъективно.
