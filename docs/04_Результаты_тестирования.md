### 3.1. Разбор RS-06

Ожидалось, что при неверном пароле роли БД приложение покажет SQLState `28P01`. Фактически HikariCP исчерпывает `connectionTimeout` и сообщает:

```
WARN ConnectionManager - Попытка подключения 1/4 не удалась: sto-pool - Connection is not available,
request timed out after 3002ms (total=0, active=0, idle=0, waiting=0)
...
Ошибка БД: Не удалось подключиться к БД за 4 попыт(ки)...
SQLState: 08001
```

**Причина:** Hikari не отдаёт исходное исключение аутентификации из `getConnection()`; наружу выходит `SQLTransientConnectionException` с `08001`.  
**Следствие:** сообщение остаётся безопасным (пароль не раскрывается), но менее точным.  
**Рекомендация:** при исчерпании попыток анализировать `SQLException.getCause()`/`getNextException()`, добавить отдельную проверку соединения с коротким таймаутом и выводить «проверьте `db.username`/`db.password`» при признаках `28xxx`.

## 5. Нефункциональное тестирование

### 5.1. Производительность запросов

Использован `EXPLAIN (ANALYZE, BUFFERS)` на текущих демо-данных. Полные планы — в `docs/evidence/explain_view.txt` и `docs/evidence/explain_report.txt`.

| Запрос | Планирование | Выполнение | Строк | Буферы | Вывод |
|---|---:|---:|---:|---:|---|
| `SELECT * FROM v_order_total ORDER BY total_cost DESC` | 3,468 мс | **0,424 мс** | 5 | shared hit=401, read=2 | приемлемо для демо-данных |
| Агрегированный отчёт по клиентам | 1,645 мс | **0,237 мс** | 3 | shared hit=287 | приемлемо для демо-данных |

Наблюдения:

1. PostgreSQL выбирает `Seq Scan` для `clients`, `cars`, `orders`, `order_services`, `order_statuses`. На таблицах в 3–6 строк это дешевле индекса и не является дефектом.
2. Соединения выполняются по ключам `o.client_id = c.id`, `o.car_id = cr.id`, `o.status_id = os.id`, `osv.order_id = o.id` — размножения строк из-за неверного JOIN нет.
3. `HashAggregate` группирует по `o.id, c.full_name, cr.plate_num, os.name`; стоимость считается через `COALESCE(SUM(price_at * quantity), 0)`.
4. Для роста данных рекомендуется добавить индекс `order_services(order_id)` и при необходимости `orders(car_id)`: сейчас индексы есть на `orders(client_id)`, `orders(master_id)`, `orders(status_id)`, `cars(client_id)`.
5. Планирование занимает больше выполнения из-за холодного кэша каталога; при повторных запросах время снижается.

## 8. Вывод

Автоматические тесты (59/59) и функциональные кейсы (20/20) подтверждают работоспособность модуля: операции с заявками, расчёт стоимости, триггеры, журнал, ограничения целостности и разграничение доступа по ролям работают согласованно. Нефункциональная проверка показала приемлемое время выполнения на демо-данных и читаемый SQL. Часть сценариев устойчивости (pool exhaustion, длительная сессия, диск, сеть) не выполнена из-за ограничений стенда; это зафиксировано как остаточный риск, а не скрыто. Для промышленной эксплуатации первоочередными являются вынос секретов, минимальные права роли приложения и добавление индекса на `order_services(order_id)`.
