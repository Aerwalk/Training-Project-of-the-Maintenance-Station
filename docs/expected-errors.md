# Описание модуля и список ожидаемых ошибок

Документ подготовлен по заданию 2: описание модуля доступа к БД и перечень ошибок трёх типов — синтаксических, логических и ошибок времени выполнения.

## 1. Краткое описание модуля

**Назначение:** предоставить приложению СТО безопасный и устойчивый доступ к PostgreSQL через JDBC.

**Состав:**

* `AppConfig`, `DbSettings` — конфигурация подключения из `application.properties`, `-Dconfig.file` и переменных окружения;
* `ConnectionManager` — пул HikariCP, проверка соединения, транзакции, повторные попытки;
* `RetryPolicy` — классификация временных сбоев и экспоненциальная задержка;
* `SqlExceptionTranslator` — преобразование SQLState в предметные исключения;
* репозитории `User`, `Client`, `Car`, `Master`, `Service`, `Order` — параметризованные SQL-запросы и вызовы хранимых функций;
* сервисы `AuthService`, `CatalogService`, `OrderService` — бизнес-правила и валидация;
* `ConsoleMenu`, `DemoRunner`, `StoApplication` — интерфейс и сценарии запуска.

**Взаимодействие с БД:**

* чтение — `PreparedStatement` + `ResultSet`;
* изменение — `INSERT/UPDATE/DELETE ... RETURNING`, транзакции;
* бизнес-операции — `CallableStatement` для функций `create_order`, `add_service_to_order`, `close_order`, `calculate_order_total`, `get_client_orders`;
* отчётность — представление `v_order_total`, журнал `order_status_log`.

**Границы ответственности:**

| Слой | Отвечает за | Не отвечает за |
|---|---|---|
| CLI | ввод, вывод, меню | SQL и бизнес-правила |
| Service | валидация, бизнес-правила, сообщения | физическое соединение с БД |
| Repository | SQL, маппинг, вызовы функций | UI и форматирование |
| DB-инфраструктура | пул, транзакции, retry, исключения | предметную логику |
| PostgreSQL | целостность, триггеры, функции, права | отображение ошибок пользователю |

## 2. Синтаксические ошибки

Синтаксическая ошибка — SQL-текст не может быть разобран PostgreSQL или ссылается на несуществующий объект. Обнаруживается на этапе выполнения запроса (или при инициализации схемы), обычно имеет SQLState класса `42`.

| № | Пример ошибки | Причина | Сообщение PostgreSQL | Ожидаемое исключение | Как обнаружить / предотвратить |
|---|---|---|---|---|---|
| S-01 | `SELEC * FROM orders` | опечатка в ключевом слове | `syntax error at or near "SELEC"` (`42601`) | `QueryException` | модульный тест SQL; просмотр журнала; IDE-анализ |
| S-02 | `SELECT * FROM order` | несуществующая таблица | `relation "order" does not exist` (`42P01`) | `QueryException` | запуск на чистой БД; миграционные тесты |
| S-03 | `SELECT status FROM orders` | несуществующий столбец | `column "status" does not exist` (`42703`) | `QueryException` | сверка со схемой; интеграционный тест |
| S-04 | `GRANT EXECUTE ON FUNCTION create_order(...)` до `CREATE FUNCTION` | неверный порядок DDL | `function create_order(integer, integer, integer, text) does not exist` (`42883`) | `QueryException` | **фактическая ошибка проекта**; исправлен порядок в `sto.sql`; проверка `docker compose up` на чистом томе |
| S-05 | `INSERT INTO clients (full_name) VALUES ('Иван', 'лишнее')` | число значений не совпадает с числом столбцов | `INSERT has more expressions than target columns` (`42601`) | `QueryException` | тест вставки; code review |
| S-06 | `SELECT * FROM get_client_orders('abc')` | неверный тип аргумента | `invalid input syntax for type integer` (`22P02`) | `DataIntegrityException` (класс 22) | валидация типа до вызова; тест с некорректным вводом |
| S-07 | `SELECT * FROM v_order_total WHERE order_id = ?` с пропущенным параметром | число параметров не совпадает | `No value specified for parameter 1` | `DatabaseException` | тесты репозитория; статический анализ |

**Особенность проекта:** ошибка S-04 не проявлялась при чтении кода, но остановила инициализацию Docker. Это показывает, что синтаксические/DDL-ошибки нужно проверять на чистой базе, а не только на уже развёрнутой.

## 3. Логические ошибки

Логическая ошибка — запрос выполняется без исключения, но результат не соответствует бизнес-смыслу. Такие ошибки самые опасные: их не видно по журналу, они обнаруживаются только сверкой данных и тестами.

| № | Пример ошибки | Причина | Проявление | Как обнаружить | Исправление / защита |
|---|---|---|---|---|---|
| L-01 | `JOIN cars cr ON cr.client_id = o.client_id` | соединение не по тому ключу | у клиента несколько автомобилей — строки и суммы размножаются | сверка `v_order_total` с `calculate_order_total`; тест на клиенте с двумя авто | `JOIN cars cr ON cr.id = o.car_id` |
| L-02 | `SUM(price_at * quantity)` без `GROUP BY` по всем неагрегированным полям | неверная группировка | одна сумма на несколько заявок или ошибка SQL | тест с несколькими заявками; `EXPLAIN` | группировка по `o.id, c.full_name, cr.plate_num, os.name` |
| L-03 | фильтр `WHERE status_id = 3` | «магическое число» вместо имени статуса | после изменения справочника статусов выборка неверна | тест на статусах; анализ справочника | фильтр по `order_statuses.name` или константе из справочника |
| L-04 | создание заявки для автомобиля другого клиента | нет проверки принадлежности | в заявке клиент A, автомобиль клиента B | негативный тест; проверка `car.clientId() == clientId` | проверка в `OrderService.createOrder` |
| L-05 | добавление услуги в завершённую заявку | нет проверки статуса | стоимость закрытой заявки меняется задним числом | тест `preventAddingServiceToClosedOrder` | проверка в сервисе + триггер `trigger_check_order_status` |
| L-06 | расчёт стоимости по текущей цене услуги | используется `services.price` вместо `order_services.price_at` | historical cost меняется при изменении прайса | сверка стоимости до/после изменения цены | фиксация `price_at` при добавлении услуги |
| L-07 | `closed_at` не заполняется/не очищается | статус меняется в обход триггера | завершённая заявка без даты или новая с датой | тест на `closed_at`; проверка инварианта | триггер `trigger_set_closed_at`, запрет прямых UPDATE в приложении |
| L-08 | два пользователя одновременно меняют одну заявку | lost update | результат одного изменения теряется | конкурентный тест; `SELECT ... FOR UPDATE` | оптимистическая блокировка по `updated_at`/версии или `FOR UPDATE` |
| L-09 | повторная отправка создания заявки | нет идемпотентности | дубликаты заявок | тест повторного вызова | ключ идемпотентности / уникальный бизнес-ключ |
| L-10 | клиент видит чужие заявки | нет фильтра по `client_id` | нарушение доступа | тест ролей; проверка `get_client_orders(clientId)` | фильтрация на уровне SQL и прав БД |

**Ключевой тест:** `viewTotalEqualsStoredFunctionResult` сравнивает сумму из представления с результатом хранимой функции. Если JOIN или GROUP BY изменены неверно, суммы разойдутся.

## 4. Ошибки времени выполнения

Runtime-ошибки возникают при выполнении корректного SQL из-за состояния среды или данных. Большинство из них имеет конкретный SQLState, поэтому могут быть обработаны предметно.

| № | Ситуация | SQLState | Ожидаемое исключение | Реакция приложения | Retry |
|---|---|---|---|---|---|
| R-01 | контейнер PostgreSQL остановлен | `08001` | `RetryExhaustedException` (`ConnectionUnavailableException`) | 4 попытки, затем понятное сообщение, код возврата 1 | да |
| R-02 | соединение разорвано во время работы | `08006` | `ConnectionUnavailableException` | сообщение, повтор операции на уровне получения соединения | да |
| R-03 | сервер БД перезапускается | `57P03` | `ConnectionUnavailableException` | повтор с задержкой | да |
| R-04 | превышен `connectionTimeout` | нет SQLState (Hikari) | `RetryExhaustedException` | сообщение о таймауте | да |
| R-05 | пул исчерпан | `SQLTransientConnectionException` | `RetryExhaustedException` | ожидание и сообщение | да |
| R-06 | дубликат телефона клиента | `23505` | `DuplicateKeyException` | «Клиент с телефоном ... уже существует» | нет |
| R-07 | дубликат гос. номера | `23505` | `DuplicateKeyException` | сообщение о дубликате | нет |
| R-08 | автомобиль для несуществующего клиента | `23503` | `ForeignKeyViolationException` | сообщение о нарушении связи | нет |
| R-09 | `NULL` в обязательном поле | `23502` | `DataIntegrityException` | сообщение о незаполненном поле | нет |
| R-10 | телефон длиннее 20 символов | `22001` | `DataIntegrityException` | сообщение о длине | нет |
| R-11 | год автомобиля вне 1950..2100 | `23514` | `DataIntegrityException` | сообщение о диапазоне | нет |
| R-12 | услуга добавлена в завершённую заявку | `P0001` (RAISE EXCEPTION) | `DatabaseException` | сообщение триггера | нет |
| R-13 | взаимная блокировка | `40P01` | `TransientDatabaseException` | повтор транзакции (рекомендуется) | да |
| R-14 | конфликт сериализации | `40001` | `TransientDatabaseException` | повтор транзакции | да |
| R-15 | нет прав на таблицу | `42501` | `DatabaseException` | сообщение администратору | нет |
| R-16 | неверный пароль роли БД | `28P01` | `ConnectionUnavailableException` | сообщение о конфигурации | нет |
| R-17 | превышение `statement_timeout` | `57014` | `DatabaseException` | сообщение о таймауте запроса | возможно |

### Ожидаемые сообщения приложения

| Сценарий | Сообщение |
|---|---|
| нет соединения | `Не удалось подключиться к БД за 4 попыт(ки). Проверьте, что контейнер PostgreSQL запущен и параметры db.* корректны.` |
| дубликат клиента | `Клиент с телефоном +7-... уже существует` |
| неверный пароль | `Неверный логин или пароль` |
| закрытая заявка | `Нельзя добавить услугу в заявку со статусом «завершена»` |
| чужая машина | `Автомобиль А123ВС64 принадлежит другому клиенту (id=2)` |
| обязательное поле | `Поле «ФИО клиента» обязательно` |

## 6. Профилактика ошибок

1. **Чистая БД в тестах.** Инициализировать схему с нуля, а не проверять только на существующей базе.
2. **Ограничения в БД.** `NOT NULL`, `UNIQUE`, `CHECK`, `FK` должны дублировать бизнес-правила, а не заменяться проверками только в Java.
3. **Параметризованные запросы.** Никакой конкатенации пользовательских значений; динамические идентификаторы (имена таблиц) — только из белого списка.
4. **Тесты на известных данных.** Эталонные суммы, количество строк, статусы и даты.
5. **Логирование SQLState и операции.** Это позволяет быстро классифицировать сбой без вывода чувствительных данных.
6. **Retry только для временных ошибок.** Повтор `23505` или `42601` бессмысленен и скрывает дефект.
7. **Транзакции для связанных изменений.** Заявка + услуги + журнал должны быть атомарны.
8. **Регулярный code review SQL.** Проверка JOIN, GROUP BY, фильтров и прав.
