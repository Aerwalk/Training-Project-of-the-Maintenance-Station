# Модуль доступа к базе данных СТО

Учебный проект по профессиональному модулю **ПМ.01 «Разработка модулей программного обеспечения для компьютерных систем»** (УП.01.02, специальность 09.02.07).

Приложение на Java реализует модуль доступа к БД станции технического обслуживания (СТО) автомобилей. PostgreSQL развёртывается в Docker, схема подготовлена на основе файла [`finalbdsto.sql`](finalbdsto.sql) и дополнена прикладными объектами в [`sto.sql`](sto.sql), параметры подключения вынесены в `application.properties`.

Основной интерфейс — настольное приложение **JavaFX**, которое работает с реальными данными PostgreSQL напрямую через сервисы `AuthService`, `CatalogService` и `OrderService` (без HTTP и JSON). Консольный режим сохранён для демонстрации модуля доступа к данным и автоматических проверок.

## Быстрый старт

### 1. Запуск PostgreSQL в Docker

```powershell
docker compose up -d
docker compose ps
```

При первом запуске автоматически выполняются:

* [`sto.sql`](sto.sql) — таблицы, индексы, представление, роли, права, функции и триггеры;
* [`docker/init/02_seed.sql`](docker/init/02_seed.sql) — демонстрационные пользователи, клиенты, автомобили, услуги и заявки.

Проверить готовность:

```powershell
docker exec sto-postgres pg_isready -U postgres -d sto
```

Параметры стенда по умолчанию: `localhost:5434`, БД `sto`, суперпользователь `postgres/postgres`.
Порт и пароль можно изменить через переменные окружения (см. `.env.example`).

Полный сброс БД (удаляет том с данными и выполняет init-скрипты заново):

```powershell
docker compose down -v
docker compose up -d
```

### 2. Сборка и запуск приложения

```powershell
.\mvnw.cmd clean package
java -jar target\sto-db-module.jar
```

Linux/macOS:

```bash
./mvnw clean package
java -jar target/sto-db-module.jar
```

Без аргументов открывается окно JavaFX. Режимы запуска:

```powershell
java -jar target\sto-db-module.jar              # графический интерфейс JavaFX
java -jar target\sto-db-module.jar --console    # интерактивное меню в терминале
java -jar target\sto-db-module.jar --demo       # сквозной демонстрационный сценарий
java -jar target\sto-db-module.jar --check      # проверка соединения и версии PostgreSQL
java -jar target\sto-db-module.jar --list-orders
java -jar target\sto-db-module.jar --help
```

Для запуска JavaFX-интерфейса из исходников без сборки jar:

```powershell
.\mvnw.cmd javafx:run
```

При первом запуске Maven скачает JavaFX и платформенные библиотеки с Maven Central.

### 3. Тестовые учётные записи

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | `admin123` | администратор |
| `manager` | `manager123` | мастер-приёмщик |
| `master` | `master123` | автомобильный мастер |
| `client` | `client123` | клиент СТО |

Логин вводится без учёта регистра. Пароли хранятся в БД в виде bcrypt-хешей (`pgcrypto`, `crypt()`); в коде и в логах пароли не сохраняются.

### 3.1. Создание учётной записи через SQL

Учётную запись можно создать без приложения — функцией `create_account()`. Она объявлена в [`sto.sql`](sto.sql), поэтому доступна сразу после `docker compose up -d`. Пароль передаётся в функцию в открытом виде, но хешируется внутри PostgreSQL (`app_hash_password`, bcrypt со стоимостью 10) и сохраняется только в `users.password_hash`.

Подключитесь к БД:

```powershell
docker exec -it sto-postgres psql -U postgres -d sto
```

Создание клиента (заодно создаётся карточка в `clients`):

```sql
SELECT create_account(
    'ivanov',                 -- логин, регистр не важен
    'ClientPass123',          -- пароль, не короче 8 символов
    'Иванов Иван Иванович',
    'client',
    '+7 900 111-22-33',       -- телефон
    'ivanov@example.com'      -- e-mail (необязателен)
);
```

Создание сотрудника (карточка `clients` не нужна):

```sql
SELECT create_account('petrov', 'MasterPass123', 'Петров Пётр', 'master');
```

Привязка к уже существующей карточке клиента (например, id = 2 из демонстрационных данных):

```sql
SELECT create_account(
    'petrova', 'ClientPass456', 'Петрова Мария Сергеевна', 'client',
    p_client_id => 2
);
```

Аргументы функции: логин, пароль, ФИО, прикладная роль (`admin`, `manager`, `master`, `client`), телефон, e-mail и id существующей карточки клиента. Обязательны первые четыре; для новой карточки клиента обязателен телефон. Функция проверяет роль, уникальность логина и телефона, минимальную длину пароля и создаёт запись в `user_security`. Созданная учётная запись сразу подходит для входа в приложение.

Проверить пароль по сохранённому хешу:

```sql
SELECT username, app_check_password('ClientPass123', password_hash) AS password_ok
FROM users WHERE username = 'ivanov';
```

Права на `create_account()` и `app_check_password()` выданы только роли `sto_admin`; у остальных ролей PostgreSQL `EXECUTE` отозван. Открытый пароль при вызове кратковременно виден в `pg_stat_activity` и может остаться в истории `psql`, поэтому для промышленной эксплуатации используйте защищённый канал и очищайте историю.

### 4. Разграничение по ролям

После входа интерфейс показывает только доступные роли разделы и операции. Проверка выполняется в навигации и повторно в сервисах, поэтому действие нельзя вызвать в обход меню.

| Возможность | admin | manager | master | client |
|---|:---:|:---:|:---:|:---:|
| Обзор, клиенты, автомобили, мастера | да | да | да | — |
| Заявки: просмотр | все | все | все | только свои |
| Создание заявки | да | да | — | — |
| Добавление услуг и закрытие | да | да | да | — |
| Создание клиентов и автомобилей | да | да | — | — |
| Услуги: просмотр | да | да | да | да |
| Услуги: создание и изменение прайса | да | — | — | — |
| Журнал статусов | да | да | — | — |

Права заданы в `model/RolePermissions.java`, разделы привязаны к правам в `ui/Navigation.java`. Клиент привязан к карточке клиента через `users.client_id`, поэтому видит только собственные заявки; сотрудники — все заявки. Те же ограничения продублированы в `sto.sql` ролями `sto_admin`, `sto_manager`, `sto_master`, `sto_client` и представлением `v_my_orders`.

## Настройка подключения

Файл [`src/main/resources/application.properties`](src/main/resources/application.properties):

```properties
db.url=jdbc:postgresql://localhost:5434/sto
db.username=sto_admin
db.password=admin_pass
db.pool.maximumPoolSize=5
db.retry.maxAttempts=4
```

Приоритет источников:

1. переменные окружения `STO_DB_URL`, `STO_DB_USERNAME`, `STO_DB_PASSWORD`, `STO_DB_MAX_POOL_SIZE`, `STO_DB_RETRY_MAX_ATTEMPTS`;
2. файл, указанный через `-Dconfig.file=D:\path\application.properties`;
3. `application.properties` в classpath.

Пароль в репозитории приведён только для локального учебного стенда. Для реального запуска используйте переменную `STO_DB_PASSWORD` или хранилище секретов.

Если база недоступна, окно JavaFX показывает экран ошибки с кнопкой повторного подключения и подсказкой проверить контейнер.

## Возможности приложения

### Интерфейс JavaFX

* экран входа с демонстрационными учётными записями, показом пароля и регистронезависимым логином;
* дашборд: счётчики заявок, кольцевая диаграмма статусов, активные заявки, выручка, последние события журнала и наполнение справочников;
* заявки: фильтры по статусу, поиск, создание, карточка заявки, добавление услуг, закрытие с записью в журнал;
* клиенты: карточки, создание, карточка клиента с автомобилями и историей заявок, быстрый переход к новой заявке;
* автомобили, услуги и мастера: справочники, поиск, создание записей, показатели прайс-листа и загрузки мастеров;
* журнал статусов с фильтром по заявке;
* тёмный sidebar, карточки, бейджи, модальные окна и toast-уведомления в едином стиле интерфейса;
* разграничение доступа: меню и кнопки формируются по правам роли, клиент видит только свои заявки;
* все данные читаются и записываются в PostgreSQL напрямую через сервисы модуля, моки не используются;
* запросы к БД выполняются в фоновом пуле потоков, интерфейс обновляется в FX-потоке через `Platform.runLater`.

### Консольный режим (`--console`)

* аутентификация пользователя по логину/паролю (проверка bcrypt-хеша средствами PostgreSQL);
* просмотр заявок через представление `v_order_total` с расчётом стоимости;
* создание заявки, добавление услуг, закрытие заявки через хранимые функции `create_order`, `add_service_to_order`, `close_order`;
* расчёт стоимости через `calculate_order_total`;
* список заявок клиента через `get_client_orders`;
* работа со справочниками клиентов, автомобилей, услуг и мастеров;
* просмотр журнала изменений статусов `order_status_log`;
* ролевое меню (администратор, менеджер, мастер, клиент);
* повторные попытки подключения при временной недоступности БД;
* трансляция `SQLException` в предметные исключения (дубликат, FK, NOT NULL, разрыв связи, синтаксис SQL).

## Примечание к `sto.sql`

Схема подготовлена на основе исходного файла [`finalbdsto.sql`](finalbdsto.sql) и дополнена тем, что требуется приложению:

* поле `users.client_id` и уникальный индекс — привязка учётной записи к карточке клиента;
* представление `v_my_orders` — заявки только текущего клиента по сессионной переменной `app.client_id`;
* таблицы `user_security` и `login_attempts`, функции `register_login_attempt`, `is_user_blocked`, `unblock_expired_users` — заготовка защиты от подбора пароля;
* расширение `pgcrypto` и функции `app_hash_password`, `app_check_password`, `create_account` — bcrypt-хеширование и создание учётных записей средствами PostgreSQL (см. раздел 3.1);
* роли `sto_admin`, `sto_manager`, `sto_master`, `sto_client`, группа `sto_readonly_group` и выдача прав;
* порядок выполнения исправлен: блок `GRANT EXECUTE ON FUNCTION ...` расположен после создания функций, иначе `docker-entrypoint-initdb.d` останавливал инициализацию с ошибкой `function ... does not exist`.

Демонстрационные данные вынесены в [`docker/init/02_seed.sql`](docker/init/02_seed.sql).

## Ограничения учебного стенда

* пароли ролей БД и демонстрационных пользователей заданы в SQL-скрипте и предназначены только для локального запуска;
* приложение подключается к БД под ролью `sto_admin`; для промышленной эксплуатации следует создать отдельную роль с минимально необходимыми правами. Ограничения `sto_manager`, `sto_master` и `sto_client` приведены в `sto.sql` как демонстрация разграничения на уровне PostgreSQL;
* разграничение интерфейса выполняется по роли пользователя, но клиент работает с БД напрямую, поэтому окончательная защита опирается на права ролей PostgreSQL;
* заблокировать учётную запись после неудачных входов можно функциями `user_security`, однако в текущей версии `AuthService` их не вызывает, чтобы демонстрационные учётные записи не блокировались при тестировании;
* консольный режим оставлен для демонстрации модуля доступа к данным, а JavaFX — для наглядной работы с той же базой;
* автотесты покрывают модуль доступа к данным, права ролей и форматирование; сам интерфейс проверяется ручным и программным smoke-тестом.
